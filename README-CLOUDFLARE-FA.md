# راهنمای فنی و وضعیت واقعی Dabernaz روی Cloudflare

این سند وضعیت واقعی معماری و محیط Preview را توضیح می‌دهد. فایل‌های قدیمی راه‌اندازی که ادعای شروع خودکار بازی با اولین درخواست مرورگر یا ساخت Schema در هر درخواست API دارند، دیگر مرجع اجرای فعلی نیستند.

## معماری موردنظر پروژه

- **Cloudflare Pages + Pages Functions**: رابط وب فارسی و APIهای احراز هویت، حساب، کیف پول، تورنومنت و مسیرهای کاربر.
- **D1**: منبع پایدار کاربران، نشست‌ها، موجودی، تراکنش‌ها، دفترکل، خریدها، کارت‌ها و دورهای بازی.
- **Worker مستقل**: هماهنگ‌کننده درخواست‌های اتاق و فراخوانی Durable Object.
- **Durable Object (یک نمونه برای هر اتاق)**: جلوگیری از اجرای هم‌زمان، مدیریت صف دورها، Alarms و بازسازی وضعیت از D1.
- **D1 batch**: مرز تراکنشی عملیات مالی و تغییرات مرتبط.
- **Outbox**: ثبت پایدار رویدادهای خرید، شروع دور، پایان دور و بازپرداخت برای هماهنگی و بازیابی.

کد Worker در `workers/room-coordinator/` قرار دارد. وجود کد و فایل Wrangler به‌تنهایی به معنی Deploy شدن Worker یا اتصال Service Binding نیست.

## وضعیت Preview در ۱۸ نوامبر ۲۰۲۶

- Pages Project: `dabernaz`.
- شاخه Preview: `test/playwright-audit`.
- دامنه Preview: `https://test-playwright-audit.dabernaz.pages.dev`.
- دستور Build: `npm run build:pages`.
- پوشه خروجی: `dist`.
- Binding فعلی D1 با نام `DB` به دیتابیس آزمایشی `dabernaz-preview` وصل است.
- Migrationهای نسخه 0 تا 3 روی همین D1 آزمایشی ثبت و راستی‌آزمایی شده‌اند.
- Worker هماهنگ‌کننده هنوز در حساب Cloudflare Deploy نشده است.
- Namespace مربوط به Durable Object در حساب Cloudflare ایجاد نشده است.
- Pages Service Binding به نام `ROOM_COORDINATOR` در تنظیمات Preview وجود ندارد.

بنابراین **API اتاق‌های پولی در Preview باید با HTTP 503 و کد `ROOM_COORDINATOR_UNAVAILABLE` بسته بماند** تا Worker و Binding به‌درستی متصل شوند. نباید از Node/PHP fallback به‌عنوان جایگزین مالی استفاده شود.

Health API در کد جدید وضعیت D1، نسخه Schema و وجود Binding هماهنگ‌کننده اتاق را جداگانه نمایش می‌دهد. اگر D1 آماده باشد ولی Worker متصل نباشد، پاسخ باید `readiness=degraded` و قابلیت `paid_rooms` را غیرفعال اعلام کند؛ `ok=true` در این حالت فقط زنده‌بودن API پایه را نشان می‌دهد، نه آماده‌بودن بازی.

## Migration و پشتیبان‌گیری

Migrationهای اجراشده فقط روی D1 آزمایشی:

- `migrations/0000_core_schema.sql` — ثبت Schema پایه و جدول‌های سازگار با پروژه.
- `migrations/0001_room_rounds_financial_queue.sql` — دورهای مستقل، خرید یکتا، کارت‌ها، بازپرداخت، جایزه، دفترکل، صف Outbox و Triggerهای جلوگیری از UPDATE/DELETE دفترکل.
- `migrations/0002_wallet_request_idempotency.sql` — کلیدهای idempotency برای درخواست‌های کیف پول.
- `migrations/0003_tournament_entry_idempotency.sql` — جلوگیری از ثبت‌نام تکراری تورنومنت.

جدول `schema_migrations` نسخه‌های 0، 1، 2 و 3 را ثبت کرده است. جدول‌ها، Triggerها و ایندکس‌های اصلی بررسی شده‌اند. هیچ Migration روی D1 Production اجرا نشده است.

Cloudflare Export برای D1 Preview وضعیت `complete` گزارش کرده و فایل SQL را در یک بخش بارگذاری کرده است. اما دریافت فایل Export از نشانی موقت امضاشده در محیط ممیزی با HTTP 403 مسدود شد؛ بنابراین محتوای Backup به‌صورت مستقل دانلود و بررسی نشده است. همچنین `PRAGMA integrity_check` از API به علت محدودیت مجوز SQLite اجرا نشد. این محدودیت باید در گزارش‌ها صریح بماند.

هر Migration بعدی باید جداگانه بازبینی، Backup و تأیید شود؛ به D1 Production دست نزنید.

## قوانین قطعی اتاق‌های دبرنا

- قیمت اتاق‌ها: 5,000، 10,000، 20,000 و 50,000 تومان.
- مهلت ثبت‌نام: 150 ثانیه از اولین خرید پایدار.
- حداقل بازیکن: 2 نفر.
- سقف کارت برای هر کاربر در هر دور: 5.
- اگر پس از 150 ثانیه یک بازیکن وجود داشته باشد، دور لغو و خریدهای معتبر دقیقاً یک بار بازپرداخت می‌شوند.
- اگر بازیکنی وجود نداشته باشد، دور بدون بازپرداخت بسته می‌شود.
- دو یا چند بازیکن، دور را آماده شروع می‌کنند.
- اگر اتاق در حال بازی باشد، خریدهای جدید در دور مستقل بعدی ثبت می‌شوند.
- فقط یک دور در هر اتاق هم‌زمان در وضعیت `playing` می‌تواند باشد.
- پایان مهلت، شروع بازی و قرعه‌کشی باید سمت سرور و مستقل از باز بودن مرورگر انجام شوند.
- GET فقط خواندن است و نباید وضعیت دور، زمان، موجودی یا نتیجه را تغییر دهد.

تقسیم اقتصادی: 10% جایزه خط، 75% جایزه کامل و باقیمانده دقیق تا 100% به کمیسیون تعلق می‌گیرد. باقیمانده محاسبه، اثر گردکردن را نیز پوشش می‌دهد؛ قبل از اعلام آمادگی مالی باید مبالغ نهایی از روی دفترکل تطبیق داده شوند.

## احراز هویت، مالی و Legacy

- نشست‌های Cloudflare با توکن تصادفی نگهداری می‌شوند؛ مقدار ذخیره‌شده در D1 هش‌شده است.
- رمزهای جدید با PBKDF2-HMAC-SHA256 ذخیره می‌شوند.
- Cookie نشست باید HttpOnly، Secure در HTTPS و SameSite مناسب داشته باشد.
- APIهای حساس هویت را از نشست معتبر سمت سرور استخراج می‌کنند؛ شناسه کاربر ارسالی مرورگر قابل اعتماد نیست.
- خرید، بازپرداخت و جایزه اتاق باید در D1 batch و با شناسه یکتا/قیدهای Unique انجام شوند.
- دفترکل `financial_ledger` Triggerهای جلوگیری از UPDATE و DELETE دارد.
- پرداخت بانکی واقعی یا درگاه Production در این Preview فعال نیست. درخواست‌های واریز/برداشت دستی فقط با داده آزمایشی و بررسی مدیریتی تست شوند.

فایل‌های `server.js` و `api.php` مسیرهای Legacy مبتنی بر JSON محلی هستند و با D1/Worker هم‌ارز نیستند. در حالت عادی API آن‌ها باید با HTTP 503 و کد `NODE_FALLBACK_DISABLED` یا `PHP_FALLBACK_DISABLED` Fail-Closed شود. فقط تست‌های CI با پوشه موقت و متغیر تست می‌توانند آن‌ها را فعال کنند. فایل PHP قدیمی که قبلاً از میزبانی cPanel ارسال شده، نسخه‌ای متفاوت و قدیمی‌تر است و نباید به‌عنوان Backend فعال استفاده شود.

## بازی‌های دیگر و تورنومنت

سنگ‌کاغذقیچی و دوز از مسیر API سمت سرور Session می‌گیرند و حرکت/نتیجه از روی ورودی معتبر محاسبه می‌شود؛ نتیجه خوداظهاری `/api/games/result` رد می‌شود. در نسخه فعلی این بازی‌ها فقط آمار بازی را تغییر می‌دهند و مسیر شرط/جایزه پولی مستقل ندارند.

قوانین ورودی تورنومنت: ساده 20 BingoCoin و بینگو 100 BingoCoin. پاداش‌های 1 و 2 BingoCoin برای برد خطی و کامل در اقتصاد بازی باید با دفترکل و آزمون مستقل تطبیق داده شوند. Workflow زمان‌بندی موجود در شاخه اصلی به OIDC با Subject/Workflow/Ref پین‌شده متکی است و به API دامنه اصلی می‌زند؛ این سازوکار را نباید به‌عنوان زمان‌بند Preview در نظر گرفت.

## تست‌ها و اجرای ممیزی

Workflowهای شاخه آزمایشی:

- `playwright-audit.yml`: Chromium محلی و Chromium روی Preview به‌صورت فقط‌خواندنی؛ درخواست‌های نوشتنی هم‌مبدأ قبل از ارسال مسدود می‌شوند.
- `room-coordinator-audit.yml`: تست D1/ Durable Object محلی و تست‌های ایزوله Worker، Node/PHP fallback، قوانین تورنومنت، UI بازی‌ها، PWA و بسته صوتی.

تست مرورگر، تست منطق مالی و آزمون Worker/DO سه چیز متفاوت‌اند؛ موفقیت هرکدام فقط همان حوزه را پوشش می‌دهد. نبود آزمون، نتیجه نامشخص است و نباید به‌عنوان قبولی گزارش شود.

## بسته صوتی فارسی

در Commit بررسی‌شده، بسته Sage Woman در مخزن موجود است: مانیفست `assets/voice/sage-woman.json` شامل ۹۰ شماره با زمان‌بندی و متن فارسی است، `configured=true` است و فایل `assets/voice/sage-woman.mp3` وجود دارد. اعتبارسنجی CI در اجرای ۱۷ نوامبر ۲۰۲۶ اعلام کرد «all 90 clips validated» و مدت فایل را 90.498912 ثانیه خواند.

این اعتبارسنجی ساختاری فایل و مانیفست را تأیید می‌کند؛ پخش آکوستیکی توسط انسان روی دستگاه‌های واقعی Android و مرورگرهای هدف هنوز باید جداگانه انجام شود. آزمون UI نیز قرارداد Audio Manager و انتخاب موتور را می‌سنجد و به‌تنهایی کیفیت صدا را تضمین نمی‌کند.

## اجرای Build و Preview

```bash
npm ci
npm run check
npm run build:pages
```

Preview روی شاخه `test/playwright-audit` ساخته می‌شود. برای API، Binding با نام دقیق `DB` لازم است. برای فعال‌شدن اتاق‌ها، Worker هماهنگ‌کننده و Service Binding با نام دقیق `ROOM_COORDINATOR` نیز لازم است؛ در وضعیت فعلی آن Binding وجود ندارد. تغییر زیرساخت Preview باید قبل از اجرا از نظر هزینه، اثر و Rollback بررسی شود.

## ممنوعیت‌ها

- `main`، Production Pages، D1 اصلی، DNS و Secretهای Production را تغییر ندهید.
- هیچ تراکنش یا حساب واقعی را برای تست استفاده نکنید.
- با Wrangler در Termux کار نکنید؛ Wrangler فقط در CI/محیط سازگار یا از روش Cloudflare مدیریت شود.
- PHP/Node fallback را برای دورزدن خطای Worker فعال نکنید.
- این نسخه تا رفع تمام موانع Critical/High و اجرای سناریوهای مالی/چندنفره، برای دریافت پول واقعی یا انتشار عمومی آماده اعلام نمی‌شود.
